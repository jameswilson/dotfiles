# Architecture

## Principle

The portable unit is an artifact or protocol, not a shared vendor directory. Canonical semantic content lives here; each harness receives a deliberately scoped projection.

## Information classes

| Class | Format | Lifetime | Loaded automatically |
|---|---|---|---|
| Durable facts | TOML for structured facts; Markdown for narrative facts | Long-lived, reviewed when changed | Only when relevant to a target |
| Preferences | Markdown, one atomic rule per bullet | Long-lived | Yes, in selected global targets |
| Procedures | Markdown, one action or constraint per bullet | Long-lived and testable | Yes, only in applicable agent targets |
| Task state | Markdown with an explicit `As of` date | Short-lived | No, except in an intentional summary projection |
| Raw history | Verbatim dated snapshots | Append-only evidence | Never |
| Procedural skills | Agent Skills packages with `SKILL.md` | Versioned reusable workflows | Discovered progressively by the harness |

## Formatting

- Use TOML for stable scalar values, lists, identifiers, and target mappings.
- Use Markdown bullets for independently editable facts, preferences, and rules.
- Use nested bullets only for qualifiers or ordered substeps.
- Use prose for rationale and target-specific narrative summaries.
- Avoid comma-separated lists when items may be added, removed, reordered, or scoped independently.
- Preserve provider formatting verbatim under `imports/`.
- Generated targets may adapt wording and structure to platform constraints.
- A constrained platform field may use a compact authored adapter under `source/adapters/`; the adapter is reviewed against the canonical semantic sources and then copied into `dist/`.

## Precedence

1. Explicit instructions in the current request.
2. Project or subtree instructions closest to the active work.
3. Applicable global procedures and preferences.
4. Durable facts.
5. Dated current state.
6. Raw history, which is evidence only and never an instruction source.

## Conflict resolutions

- Concision versus depth: default to 120 words, but exceed that when explicitly requested or when brevity would materially reduce correctness.
- Avoiding follow-up questions versus resolving ambiguity: make reasonable assumptions by default; ask only when missing information materially changes scope, authorization, risk, or the result.
- Strong global rules versus project reality: current repository evidence and closer project instructions override generic global conventions.
- Shared behavior versus harness capability: generate native adapters instead of assuming every harness interprets the same file identically.
- Shared memory versus context flooding: retrieve selected, source-backed context instead of preloading raw histories or complete memory stores.

## Storage boundaries

- `~/.config/agent-instructions/`: authored configuration and generated projections.
- `~/.agents/skills/`: installed Agent Skills runtime, including links to canonical authored checkouts.
- Dedicated skill repositories: canonical personally authored cross-agent workflows; link or install their packages into `~/.agents/skills/`.
- `$XDG_STATE_HOME/skills/.skill-lock.json`: tool-generated skill installation state when `XDG_STATE_HOME` is set; otherwise `~/.agents/.skill-lock.json`.
- `~/.codex/`, `~/.cursor/`, and similar directories: vendor-owned configuration, runtime state, and native deployment targets.
- Platform-hosted memory and personalization: remote state mirrored only through explicit dated imports.

## Skills and commands

- Agent Skills are the canonical portable workflow format and may package progressively loaded instructions, scripts, references, and assets.
- Built-in slash commands are harness controls, not shared artifacts.
- Do not maintain user-authored command copies of migrated skills. Add a thin alias only when a harness cannot invoke the skill natively.

## Cursor adapter

- Cursor User Rules are account-backed, cloud-synced objects with a title and Markdown content. They are the primary global Cursor deployment surface.
- Cursor project rules remain `.cursor/rules/*.mdc`; keep them project-scoped unless a specific global Cursor surface has been verified to load `~/.cursor/rules/`.
- Cursor's app-control MCP can list, add, update, and remove User Rules, but it is available inside Cursor's Agents Window rather than as a shell API.
- Cursor also embeds the resolved User Rule bodies in local agent prompt snapshots under `User/globalStorage/state.vscdb` in `cursorDiskKV`. This is a secondary cache, not the live rule store: it omits cloud ids and remains stale until a new prompt captures current rules.
- Export remote rules verbatim before reconciliation. Never delete or overwrite unmanaged rules merely because a generated managed rule exists.
- Deploy only exact-title managed rules generated by this control plane. List first, refuse ambiguous duplicate-title updates, and verify after writing.
- Keep separate generated User Rules for stable semantic modules so individual Cursor rules remain reviewable and can be updated without replacing an unrelated rule.
